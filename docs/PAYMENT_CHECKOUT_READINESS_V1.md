# Payment Checkout Readiness V1

Status: **OFFLINE CONTRACT ONLY**

This layer prepares the payment-initiation side for a future concrete provider without enabling checkout or making any provider call today.

## Problem it solves

Provider checkout/session creation is an external side effect. A timeout can leave the caller unsure whether the provider created a payment session. Retrying naively can create duplicate provider payments or duplicate local attempts.

Payment Checkout Readiness V1 makes the local side retry-safe before a provider is connected.

## Request-key identity

`requestKey` is the stable retry identity for initiating one payment attempt.

`createOrReplayPaymentIntentAttemptV1()` behaves as follows:

- first valid request creates the Payment Contract V1 intent and attempt;
- an exact retry with the same `requestKey` returns the stored canonical intent/attempt ids;
- proposed UUIDs may be regenerated by a retrying caller, but they never replace stored canonical ids;
- booking, quote, provider, amount and currency must match exactly;
- reusing the request key with different commercial identity fails closed;
- a different request key cannot create a second payment intent for the same booking.

A future concrete provider adapter should use this same stable retry identity as the provider-side idempotency key when the provider supports idempotent checkout/session creation.

## Provider reference binding

`bindPaymentProviderReferenceV1()` attaches the provider's stable payment/session reference only after a local attempt exists.

Rules:

- attempt, booking, quote, provider, amount and currency must match;
- the first matching reference is attached to the attempt;
- an exact retry is idempotent and returns the existing reference;
- a different reference cannot replace an already-bound reference;
- the same `(provider, provider_reference)` cannot be bound to another attempt;
- no provider secret, redirect URL, raw provider payload or guest PII is persisted by this layer.

## Intended future ordering

When a real provider is selected, the reviewed integration should preserve this order:

1. validate booking/quote/commercial identity;
2. persist or replay the local intent/attempt by stable `requestKey`;
3. call the provider with the same stable idempotency identity where supported;
4. bind the returned provider reference to that exact attempt;
5. return only provider-safe checkout material needed by the client;
6. rely on the verified webhook pipeline for authoritative payment state changes.

If the provider call times out, retry with the same `requestKey`. Do not create a new local payment intent merely because the network result is unknown.

## PostgreSQL evidence

The disposable PostgreSQL contract suite verifies:

- first creation versus exact request-key replay;
- regenerated proposed UUIDs cannot replace canonical ids;
- commercial mismatch on replay is rejected;
- a second request key cannot create another intent for the same booking;
- provider-reference attachment and exact replay;
- reference replacement is rejected;
- cross-attempt provider-reference collisions are rejected.

## Production gate remains closed

This work does not add or change:

- a concrete payment provider;
- provider credentials or secrets;
- public checkout/session API routes;
- public payment webhook routes;
- production PostgreSQL/Neon or Hyperdrive;
- production payment migrations;
- checkout activation;
- DNS or production deployment.

Payment Contract V1 and this readiness layer remain offline until the real production database target and provider are explicitly selected and reviewed.
